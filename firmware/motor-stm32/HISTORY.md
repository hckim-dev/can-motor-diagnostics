# 모터 STM32 개발 기록

의미 있는 작업을 마치면 [공통 양식](../../docs/development-history.md)에 따라 기록합니다.

## 2026-11-25 · CAN 내부 루프백 시험 코드 반영

- **담당·근거** — 권민지(모터 STM32), [`motor_mcu.ioc`](motor_mcu.ioc), [`main.c`](Core/Src/main.c)와 [`can_com.c`](Core/Src/can_com.c).
- **문제** — 외부 CAN 장비 연결에 앞서 STM32가 보낸 프레임을 자체 수신하고 데이터가 일치하는지 확인할 방법이 필요했다. 빌드에 필요한 CMSIS-RTOS2 헤더와 모터 제어 선언도 정리해야 했다.
- **판단과 변경** — CAN을 125 kbit/s 내부 루프백으로 설정하고, 시작 시 표준 ID `0x123`의 8바이트 시험 프레임을 송신해 FIFO0 수신값을 비교하도록 했다. 모터 제어 선언 오류를 수정하고 누락된 FreeRTOS 헤더를 추가했다.
- **검증** — ARM GCC로 소스 36개를 컴파일하고 `motor_mcu.elf` 링크까지 완료했다. 이번 변경의 실물 CAN 내부 루프백과 외부 CAN 통신 검증은 미실행이다.

## 2026-11-24 · JP5 전원 선택 변경으로 ST-LINK 연결 복구

- **담당·근거** — 권민지(모터 STM32), [전원 측정 사진과 디버그 기록](https://app.notion.com/p/4224894796bd8180bb42f93f4f1d25f9), CubeProgrammer v2.16.0 로그, `motor_mcu.ioc`와 HAL 초기화 코드.
- **문제** — CAN 내부 루프백 준비 중 `Target is not responding`과 레지스터 읽기 실패가 발생했다. 외부 브레드보드 배선을 빼도 실패가 반복됐다.
- **판단과 변경** — CAN RX는 PA11(CN10-14), TX는 PA12(CN10-12)임을 확인했다. USB 입력 U5V는 5.14 V였으나 보드 5V는 약 2.07–2.09 V, 3V3는 2.06 V였다. USB로 전원을 공급하는 보드의 JP5 점퍼 캡을 U5V 위치로 옮겼다.
- **검증** — 변경 후 오실로스코프에서 5V는 5.11 V, 3V3는 3.39 V로 측정됐다. ST-LINK 펌웨어 V2J44M29, SWD 4 MHz, Under Reset 조건에서 CubeProgrammer가 NUCLEO-F103RB의 대상 MCU(ID 0x410)를 인식했다. 대상 전압은 3.26 V였고, 0x08000000에 23.20 KB를 다운로드한 뒤 `Download verified successfully`를 확인했다. 로컬 ARM GCC 빌드와 링크도 완료했다. 실물 CAN 내부 루프백과 외부 CAN 송수신은 미확인이다.

## 2026-11-20 · 방향 입력 해제에 따른 모터 정지 구조 설계

- **담당·근거** — 권민지(모터 STM32), 기존 `Core/Src/motor_control.c`의 `start`·`stop` 분기와 앞·뒤 버튼 해제 동작에 대한 설계 논의
- **문제** — 기존 구조는 `start`가 참일 때만 내부에서 `stop`을 확인했다. 시작 입력이 해제된 뒤에는 별도 STOP 입력도 검사하지 못하므로, 앞·뒤 버튼을 떼는 동작만으로 정지 절차를 시작할 수 없었다.
- **판단과 변경** — 버튼을 누르는 동안 앞·뒤 방향 신호를 주기적으로 받고, `MotorControl_OnDirection()`에서 마지막 유효 방향과 수신 시각을 기록하는 구조로 설계했다. 모터 태스크는 방향 신호가 만료되면 버튼 해제로 판단하고 저듀티 유지 후 두 PWM 채널을 0%로 내린다. 운전 허가 만료·철회나 비상정지는 저듀티 구간을 생략하고 PWM을 끄도록 구분했다. 예제에서는 두 입력의 만료 기준을 각각 200ms로 두었다.
- **검증** — 모터 태스크와 `main.c` 연결 예제는 ARM GCC 문법 검사를 통과했다. 로컬 펌웨어 반영, CAN 연동, 실물 버튼 해제 및 정지 검증은 미실행이다.
- **후속 확인** — 로컬 `motor_mcu` CubeIDE 프로젝트를 저장소에 추가했다. 첫 ARM GCC 검사에서 모터 제어 선언 불일치, 함수 선언 위치 오류 및 CMSIS-RTOS2 헤더를 찾지 못하는 오류가 보고됐다. CubeIDE 프로젝트의 헤더 경로를 적용해 `motor_control.c`와 `main.c`의 문법을 다시 검사했다. 헤더 오류는 재현되지 않았으며, `MotorDirection` 타입 불일치와 `motorTask()` 내부의 잘못된 함수 선언으로 문법 검사가 실패했다. 이번 점검에서 전체 빌드, CAN 연동 및 실물 검증은 미실행이다.
