# Backend 개발 기록

의미 있는 작업을 마치면 [공통 양식](../docs/development-history.md)에 따라 기록합니다.

## 2026-11-20 · 모의 시험 판정·기록·리플레이

- **담당·근거** — Codex · 설계서 v1.5 C8~C10, [합성 NO_EDGE 예제](../tests/fixtures/diagnostic-no-edge.jsonl), [판정·리플레이 회귀 시험](../tests/check_diagnostics.py)
- **문제** — CAN 상태·고장과 UART 관측을 동일 시험 회차에 연결하고, 판정에 사용한 원본과 설정을 보존해 같은 결과를 재현해야 했습니다.
- **판단과 변경** — 기존 CAN·UART 수신기를 공통 입력 순번으로 연결했습니다. 고정 파형 세 시나리오를 판정하고, GAP_500은 `END` 뒤 500ms 안의 새 CAN 상태·고장 보고를 요구합니다. 기록은 원본과 결과를 동기화한 뒤 완료하며, 리플레이는 원본 설정·입력 해시·결과를 검증합니다.
- **검증** — Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 89개 테스트를 통과했습니다. CLI로 NO_EDGE 합성 입력을 기록하고 1배속·빠른 재생의 결과와 증거 ID가 일치하는 것을 확인했습니다. GPIO 미검증은 판정 불가이며 원본 결과 변경은 재생 오류로 처리했습니다. 실물 CAN·UART, TCP 판정 표시, 연속 운전 기록은 별도 통합 대상입니다.
- **판정 경계 재검토** — `END` 이후 수집 마감에 UART 프레임이 일부만 남은 회차와, 주입 이전과 같은 CAN epoch에서만 기대 고장이 확인된 회차가 `PASS`로 처리됐습니다. 미완성 UART 입력은 증거 ID와 함께 남기고 주입 당시 `TEST_ACTIVE`가 확인된 epoch 이후의 기대 고장만 사용합니다. 수집 창 안에서 완료된 분할 프레임은 정상 처리하며, 전체 91개 테스트를 경고를 오류로 처리해 통과했습니다.
- **GAP_500 래치 유지 재검토** — 복귀 뒤 유효한 고장 해제 보고가 들어와도 같은 수집 창에서 다시 래치되면 마지막 상태가 앞선 해제를 덮어 `PASS`로 처리됐습니다. 일치하는 최신 상태·고장 보고에서 확인한 해제를 회차에 유지합니다. 합성 입력의 기록과 리플레이가 같은 `FAIL` 및 증거 ID를 반환했고, 전체 92개 테스트를 경고를 오류로 처리해 통과했습니다.
- **FPGA 시험 시작 전제 재검토** — `BASELINE_START`의 FPGA 관측이 `READY=0`이어도 `PASS`가 나오는 문제를 재현했습니다. GPIO 검증 시험에서 시작 시 `READY=1`을 요구하고, 근거가 없으면 `INCONCLUSIVE`를 기록합니다. 기대 고장 뒤 READY 하강은 정상 경로로 검증했습니다. 경고를 오류로 처리한 전체 93개 테스트를 통과했습니다.
- **UART 분할 입력의 증거 연결 재검토** — 여러 번에 걸쳐 수신한 프레임의 마지막 조각만 판정 근거에 남았습니다. 파서가 프레임에 포함된 각 입력의 기록 ID를 전달하고, `raw_fpga.jsonl`과 판정 결과에서 참조하도록 수정했습니다. 분할·연속 프레임, 잡음 제외, CLI 기록과 리플레이 재현을 검증했고 경고를 오류로 처리한 전체 95개 테스트를 통과했습니다.
- **종료 후 조작과 지연 CAN 보고 재검토** — `END` 후 STOP·RESET을 관측한 뒤 도착한 고장 보고가 앞선 NO_EDGE의 증거로 들어가 `PASS`가 됐습니다. 명시적 조작에서 CAN 증거 수집을 마감하고, 이전에 확보한 근거만 사용합니다. 같은 단조 시각에서 입력 순서를 바꾼 두 경우의 판정 및 원본 참조를 확인했고, 경고를 오류로 처리한 전체 96개 테스트를 통과했습니다.
- **CAN 상태 변화와 증거 마감 재검토** — `END` 뒤 CAN으로 관측한 비상정지나 모드 변경에도 지연 고장 보고로 `PASS`가 생성됐습니다. STOP·RESET과 같은 판정 경계를 적용해 변경 전 근거만 사용합니다. 두 변화의 전후 입력 순서와 CLI 리플레이 재현을 확인했고, 경고를 오류로 처리한 전체 97개 테스트를 통과했습니다.
- **기록 완료 처리 재검토** — 디렉터리 `fsync`가 실패해도 `manifest.json`이 남아 완료 기록으로 열렸습니다. 원본과 결과 파일을 먼저 동기화·닫고 완료 표시를 게시하며, 디렉터리 동기화 실패 시 표시를 회수합니다. 오류를 주입해 원본 파일은 남고 리플레이 입구에서는 거부되는 것을 확인했습니다. 경고를 오류로 처리한 전체 98개 테스트를 통과했습니다.
- **6단계 전체 검증** — `NORMAL`, `NO_EDGE`, `GAP_500` 정상 사례와 GAP 래치 재발, STOP 중단, 기록 조기 종료를 각각 CLI로 기록하고 재생했습니다. 여섯 사례의 판정·사유·증거 ID가 일치했고, NO_EDGE의 1배속과 빠른 재생 결과도 일치했습니다. 경고를 오류로 처리한 전체 98개 테스트를 통과했으며 코드 수정 사항은 발견하지 못했습니다.
- **Backend 1~6단계 전수 검증** — 전체 98개 테스트를 경고를 오류로 처리해 통과했습니다. 별도 프로세스로 읽기 전용·조작 TCP, CAN 예제 수신·만료, 가상 REAL의 시작·중복·정지·재시작, FPGA UART hex·바이너리 처리를 실행했습니다. 6단계의 정상·실패·중단·판정 불가 여섯 사례에서 기록과 재생의 판정·사유·증거 ID가 일치했습니다. 코드 수정 사항은 발견하지 못했습니다.

## 2026-07-12 · FPGA UART 수신과 시험 회차 추적

- **담당·근거** — Codex · 설계서 v1.5 C8, [UART 골든 벡터](../tests/fixtures/fpga-uart-1.0.hex), [수신 시험](../tests/check_fpga_uart.py)
- **문제** — 22바이트 UART 이벤트를 분할된 스트림에서 복원하고, 프레임 유실과 보드 재시작을 시험 회차에서 구분해야 했습니다.
- **판단과 변경** — 코덱, 스트림 파서, 회차 추적기를 분리했습니다. CRC 오류 뒤 sync를 다시 찾고, 순번 공백·잘린 프레임·FPGA 오류를 관측과 회차에 남깁니다. 순번 역행으로 세션이 불명확하면 현재 회차를 중단하고 재연결까지 보류합니다.
- **검증** — Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 76개 테스트를 통과했습니다. hex·바이너리 CLI, 정상 wrap, 잘린 EOF, 혼합 입력의 100개 분할 패턴을 확인했습니다. 실물 UART 연결과 CAN 증거를 결합한 판정은 미실행입니다.
- **회차 종료 재검토** — `END`에서 `timing_valid=1`을 보고했지만 유효한 `DIAG_EDGE`를 받지 못한 회차가 오류 없이 종료되는 문제를 재현했습니다. 회차 기록에 `MISSING_DIAG_EDGE`를 남기고, 캡처 없음을 보고한 정상 `END`와 구분합니다. 후속 `STATUS`에서도 누락 기록이 유지되며 경고를 오류로 처리한 전체 77개 테스트를 통과했습니다.
- **FPGA 오류 유지 재검토** — 유휴 `STATUS`가 overflow를 보고한 뒤 다음 회차가 오류 없이 기록되는 문제를 재현했습니다. `STATUS`의 오류는 현재 UART 세션에서 유지하고 개별 이벤트의 오류는 해당 회차에 연결합니다. 같은 세션의 오류 지속과 재연결 후 초기화를 검증했고, 경고를 오류로 처리한 전체 79개 테스트를 통과했습니다.
- **Backend 1~5단계 전수 검증** — 경고를 오류로 처리한 전체 79개 테스트를 통과했습니다. 별도 실행으로 읽기 전용 TCP의 10Hz·재접속, 조작 TCP의 준비·heartbeat 만료, CAN 예제의 측정값·만료, 가상 REAL의 시작·중복·STOP과 프로세스 재시작 시 부팅 ID 증가, UART CLI의 hex·바이너리 입력을 확인했습니다. 정상 UART 프레임 450개와 손상·잡음이 섞인 입력을 100가지 방식으로 나눠도 관측 결과가 동일했습니다. 코드 수정 사항은 발견하지 못했습니다.

## 2026-11-19 · 모의 CAN 명령과 운전 허가 검증

- **담당·근거** — Codex · [통신 규격](../docs/protocol.md), [CAN 2.1 프레임 예제](../tests/fixtures/can-2.1.jsonl), [모의 CAN 시험](../tests/check_can_control.py)
- **문제** — STM32 실물 송신 전에 TCP 조작을 CAN 명령·결과에 연결하고, STOP이 대기 명령과 연결 상실을 선점하는지 확인해야 했습니다.
- **판단과 변경** — 송신 인코더, 제어 상태, 모의 버스, TCP 연결을 분리했습니다. 송신 대기와 응답 마감을 각각 적용하고, 응답은 원래 epoch와 명령 순번을 대조합니다. 부팅 ID를 프로세스 사이에 보존하며, 모의 STOP 복구에서는 억제 송신 이후 더 큰 epoch의 정지 관측을 요구합니다.
- **검증** — Jetson Python 3.10.12에서 경고를 오류로 처리한 전체 44개 테스트를 통과했습니다. 모의 CAN의 네 명령, 순번 소진, STOP 선점, 지연 결과, 연결·세션 변경을 검증하고, TCP CLI로 가상 REAL의 시작·정지와 프로세스 재시작 시 부팅 ID 증가를 확인했습니다. 실제 CAN 송신, 어댑터의 송신 취소 범위, 실제 STOP 인과 확인은 미실행입니다.
- **재검토** — 정지 확인 없이 새 epoch에서 활성 상태가 관측되면 그 epoch에도 억제 프레임을 보내고 정지 확인 기준을 갱신합니다. 가상 모터에서 동일 CAN 명령의 결과 재사용, 이미 소비한 순번의 STOP 우선 처리, 허가 비트 해제 시 정지를 검증했습니다. Jetson에서 경고를 오류로 처리한 전체 47개 테스트를 통과했습니다.
- **단절·중복 요청 재검토** — 단절 통보 뒤에도 CAN 송신이 호출되는 문제와, 완료 결과가 대기 중일 때 동일 TCP 요청에 이전 `ACCEPTED`가 반환되는 문제를 재현했습니다. 명시적으로 재연결할 때까지 송수신을 막고, 대기 중인 최신 결과는 기존 송신 경로에서 전달합니다. 재연결 후 정지 재확인과 TCP 중복 요청을 회귀 시험에 추가했습니다. 모의 CAN을 포함한 전체 49개 테스트를 경고를 오류로 처리해 통과했습니다.
- **STOP 선점 재검토** — 같은 모의 버스 주기에 `START_REAL`과 `STOP`을 받으면 이미 큐에 넣은 `START_REAL`이 먼저 전달돼 가상 모터가 `RUNNING`에 진입했습니다. 명령 송신을 모의 버스 주기로 모아 STOP과 단절이 송신 전 명령을 취소할 수 있게 했습니다. STOP, TCP 단절, CAN 단절 각각에서 `START_REAL`이 가상 모터에 도달하지 않음을 검증했습니다. Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 50개 테스트를 통과했습니다.
- **만료 경계와 TCP 표시 재검토** — 300ms에 도착한 `MOTOR_STATE`가 이전 관측을 덮기 전에 만료를 적용해 허가를 철회하고 대기 명령을 취소합니다. 모의 버스에 전달된 조작 프레임을 수신 모듈에서도 관측해 TCP 조작 상태에 동일한 허가 유효기간을 적용했습니다. 상태 수신 299/300ms와 허가 표시 199/200ms 경계를 검증했습니다. Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 52개 테스트를 통과했습니다.
- **세션 카운터 소진 재검토** — 마지막 세션에서 STOP을 처리한 뒤 세션 번호가 0인 epoch가 생성되는 문제를 재현했습니다. 마지막 유효 epoch에서 `INTERNAL`을 한 번 기록하고 출력을 억제하며, 재허가와 `RESET`을 포함한 일반 명령을 거부합니다. REAL·TEST에서 마지막 세션의 정상 동작과 소진 이후 중복·신규 명령 거부를 검증했습니다. Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 53개 테스트를 통과했습니다.
- **명령 순번 소진 재검토** — `RESET`이 순번 255로 완료돼 가상 모터가 정지했는데도 다음 명령이 `SEQUENCE_EXHAUSTED`로 거부됐습니다. 마지막 순번을 소비하고 출력이 꺼져 있으면 기존 키로 결과를 만든 뒤 새 epoch를 발급합니다. 활성 상태에서는 STOP까지 현재 epoch를 유지합니다. 새 epoch에서 순번 1을 사용하고 이전 요청을 거부하는 동작을 검증했습니다. 경고를 오류로 처리한 전체 55개 테스트를 통과했습니다.
- **억제 송신 실패 재검토** — 첫 억제 프레임 제출이 실패하면 전송이 가능해져도 50ms를 기다려 STOP 명령이 타임아웃되는 문제를 재현했습니다. 억제 프레임은 다음 버스 주기에 재시도합니다. 송신이 빨리 복구되면 억제 프레임과 STOP 명령이 순서대로 전송되고, 명령 마감 이후에 복구되면 억제 프레임만 전송되는 것을 검증했습니다. 경고를 오류로 처리한 전체 56개 테스트를 통과했습니다.
- **CAN 허가 만료 고장 재검토** — 가상 모터에서 유효한 허가가 200ms 동안 없으면 출력은 정지했지만 `OP_LINK_LOSS`가 기록되지 않았습니다. 만료 시 고장 비트를 래치하고 새 epoch의 `FAULT` 상태를 발행합니다. 199/200ms 경계와 중복 고장 방지, CAN 재연결 이후 `RESET`과 새 `START_REAL`을 거쳐 복구하는 경로를 검증했습니다. 경고를 오류로 처리한 전체 57개 테스트를 통과했습니다.
