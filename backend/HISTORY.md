# Backend 개발 기록

의미 있는 작업을 마치면 [공통 양식](../docs/development-history.md)에 따라 기록합니다.

## 2026-11-19 · Backend 1~3단계 통합 검토

- **담당·근거** — Codex · [목업 실행 방법](README.md), [통신 규격](../docs/protocol.md), [공통 예제](../tests/fixtures/)
- **문제** — 작업 트리의 TCP 목업에 이전 조작 로직이 들어 있었고, CAN 예제 연결도 빠져 있어 통합 시험 3건이 실패했습니다.
- **판단과 변경** — TCP 목업을 기존 조작 모듈과 CAN 수신 모듈에 다시 연결했습니다. 연결 설정과 주기 송신 루프를 분리하고, CAN 프레임 분류와 이름을 규격의 필드에 맞췄습니다. 예제 공급 작업이 실패하면 실행 경로에 오류가 전달되도록 변경했습니다.
- **검증** — Jetson Python 3.10.12에서 경고를 오류로 처리한 전체 27개 테스트를 통과했습니다. 읽기 전용 TCP 전송과 CAN 예제의 TCP 측정값을 CLI에서도 재검증했습니다. 메모리 입력으로 측정 샘플 10,000개와 스냅샷 5,000개를 약 0.59초에 처리했습니다. 해당 수치는 실물 버스·어댑터 지연을 포함하지 않습니다.

## 2026-11-19 · CAN 수신과 측정 상태 검증

- **담당·근거** — Codex · [통신 규격](../docs/protocol.md), [시간순 CAN 예제](../tests/fixtures/can-rx-timed.jsonl), [CAN 수신 시험](../tests/check_can_rx.py)
- **문제** — TCP 목업의 고정 상태 대신 CAN 프레임에서 확인한 상태와 측정값을 표시하고, 결측·만료·이전 부팅의 값이 현재 상태로 남지 않게 해야 했습니다.
- **판단과 변경** — CAN 디코딩, 측정 결합, 세션 상태, 예제 공급을 분리했습니다. 수신 순번·단조 시각·원본 ID를 부여하고, 현재 부팅의 시간 프레임을 기준으로 100ms 안에 측정을 결합합니다. SOF나 어댑터 시각 대신 Jetson 수신 시각으로 유효 기간을 계산하며, 새 부팅과 연결 복구에서 300ms 동안 측정 결합을 보류합니다.
- **검증** — Jetson aarch64, Python 3.10.12에서 경고를 오류로 처리한 테스트 19건을 통과했습니다. CAN 필드·결측·만료·부팅·순번 경계와 CAN 예제에서 TCP 스냅샷까지의 흐름을 확인했습니다. `--can-fixture` 실행과 기존 읽기 전용 모드도 실제 TCP로 검증했습니다. 실물 CAN 어댑터의 지연과 CAN 송신은 미실행입니다.
- **재검토** — 이전 부팅의 시간 프레임은 폐기되지만 같은 순번의 미확정 측정값은 남아 새 부팅 샘플에 섞이는 경우를 재현했습니다. 시간 프레임에서 부팅이 다르다고 확인되면 그 순번의 미확정 묶음도 폐기합니다. 형식이 잘못된 프레임 뒤 정상 프레임이 결합 창 안에 오면 샘플 확정 전까지 교체할 수 있게 했습니다. 회귀 시험 2건을 추가해 Jetson에서 전체 21건을 통과했고, CAN 예제의 TCP 출력과 정상 종료를 다시 확인했습니다.
- **추가 경계 검증** — HELLO 만료 후 재수신만으로 이전 운전 허가가 되살아나는 경우를 재현했습니다. 같은 부팅·epoch에서는 이전 허가 순번을 기억하고 새 유효 순번을 받은 뒤에만 허가 상태를 갱신합니다. 오류가 있는 측정 프레임이 마지막에 와도 100ms 결합 창이 닫히기 전에는 확정하지 않습니다. Jetson에서 경고를 오류로 처리한 전체 23개 테스트를 통과했습니다.
- **연결 복구 검증** — 명시적으로 연결을 끊었다가 같은 모터 epoch와 조작 노드 부팅으로 복구할 때 중복 허가가 다시 유효해지는 경우를 수정했습니다. 연결 복구 시 이전 순번은 유지하고 새 순번의 wrap은 허용합니다. 모터 epoch나 조작 노드 부팅이 바뀌면 순번을 초기화합니다. Jetson에서 경고를 오류로 처리한 전체 25개 테스트를 통과했습니다.
- **최종 재검토** — 고장 표시 캐시와 마지막으로 수락한 고장 순번·마스크를 분리했습니다. 같은 epoch에서 연결 단절, HELLO 만료, 버전 불일치로 복구한 뒤에도 이전 고장은 거부합니다. 같은 순번·마스크의 반복 보고, 순번 wrap, 새 epoch 초기화를 회귀 시험에 포함했습니다. Jetson에서 경고를 오류로 처리한 전체 26개 테스트를 통과했고, 8비트 순번 256개 시작값에서 재연결 후 이전·모호 순번 거부와 정상 보고를 확인했습니다.
- **종결 검증** — 조작 노드의 새 부팅 ID를 먼저 받은 경우 기존 모터 epoch의 지연된 허가가 다시 유효해지는 문제를 수정했습니다. 더 큰 모터 epoch의 HELLO와 해당 epoch의 새 허가를 모두 받아야 허가 상태를 갱신합니다. Jetson에서 경고를 오류로 처리한 전체 28개 테스트를 통과했습니다.

## 2026-11-19 · TCP 조작 목업 검증

- **담당·근거** — Codex · [통신 규격](../docs/protocol.md), [Qt 요청 예제](../tests/fixtures/tcp-qt-to-backend.jsonl), [Python 검증 클라이언트](../tests/check_tcp_control.py)
- **문제** — Qt 앱과 CAN 연결 전에 시험 준비 명령과 heartbeat 만료, 재접속 시 요청 처리를 검증할 필요가 있었습니다.
- **판단과 변경** — `--control`에서 단일 제어 연결을 받고, `ARM_TEST` 결과와 `TEST_ARMED` 관측을 나눠 보냅니다. 유효 heartbeat가 300ms 없으면 준비를 해제합니다. 재접속 전의 요청이 다시 실행되지 않도록 목업 프로세스에 최대 255건을 보관하고, 한도 이후 새 요청은 거부합니다.
- **검증** — Jetson aarch64, Python 3.10.12에서 개발 모드와 경고를 오류로 처리하는 설정으로 조작 목업 시험 5건을 통과했습니다. 분할·합쳐진 입력, 결과와 상태, 만료, 중복·상한, 이전 연결 요청, 인자·프레이밍 오류, 동시 접속 및 종료를 확인했습니다. 읽기 전용 스냅샷 10Hz와 재접속도 재검증했습니다. Qt와 실물 CAN·UART 검증은 미실행입니다.
- **종결 검토** — TCP 입출력과 조작 상태를 별도 모듈로 분리했습니다. 잘못된 인자로 거부된 요청의 ID를 재사용하면 실행되던 문제를 재현해 최초 거부 결과도 기록하도록 수정했습니다. 같은 ID로 같은 잘못된 요청은 이전 결과를 받고, 인자를 고친 요청은 충돌로 거부됩니다. Jetson에서 조작 시험 6건을 두 차례 통과했고 읽기 전용 10Hz 전송과 재접속도 다시 확인했습니다.
- **구조 검토** — 거부된 요청까지 세던 `cmd_seq`를 요청 기록과 분리해 성공한 새 요청에만 순번을 발급합니다. 명령별 인자 범위는 한 곳에서 관리하고, 테스트의 첫 성공 응답은 공통 fixture와 대조합니다. 만료 후 다시 준비하거나 재접속해도 같은 epoch에서 순번이 이어짐을 확인했습니다. Jetson에서 경고를 오류로 처리한 조작 시험 6건을 두 차례 통과했고, 읽기 전용 모드도 다시 확인했습니다.

## 2026-11-19 · 읽기 전용 TCP 목업 검증

- **담당·근거** — Codex · [통신 규격](../docs/protocol.md), [TCP 예제](../tests/fixtures/tcp-backend-to-qt.jsonl), [목업 실행 및 검증 방법](README.md)
- **문제** — Qt 앱을 개발하기 전에 Backend의 초기 상태와 TCP 메시지 경계를 Jetson에서 독립적으로 확인할 필요가 있었습니다.
- **판단과 변경** — 표준 라이브러리로 읽기 전용 서버와 검증 클라이언트를 구현했습니다. 공통 예제와 수신 내용을 대조하고, 연결마다 `stream_id`를 발급합니다. 검토 과정에서 연결이 열린 상태의 종료 문제를 확인해 종료 시 활성 연결을 닫도록 수정했습니다. 검증 클라이언트는 이전 연결의 EOF 처리와 재접속이 겹쳐 새 연결이 `hello` 전에 닫히면 짧게 재접속합니다.
- **검증** — Jetson aarch64, Python 3.10.12에서 6회 실행했습니다. 각 실행에서 `hello → TEST / STOPPED`, 스냅샷 10간격 약 1.02초, 재접속 시 새 `stream_id`를 확인했습니다. 분할·합쳐진 메시지, LF 포함 16,384바이트 경계, 미완성 줄과 NaN 거부, 두 번째 연결 및 클라이언트 입력 차단, 활성 연결 중 SIGINT·SIGTERM 정상 종료를 확인했습니다. CAN·UART 실물 및 Windows 클라이언트 실행은 미실행입니다.
- **종결 검토** — Python 3.10에서 첫 스냅샷 이후 대기 시간이 지나면 연결이 끊기는 현상을 재현해 `asyncio.TimeoutError`를 처리하도록 수정했습니다. 검증 클라이언트는 전체 평균과 함께 스냅샷 사이의 송신 시각 차이도 확인합니다. 1초 지연 후 10개를 몰아 보낸 입력은 거부했고, 수정 후 Jetson에서 목업 6회와 접속·종료·프레이밍 검증을 통과했습니다. 쓰기 대기가 만료되면 연결 슬롯을 반환하는 동작은 모의 writer로 확인했습니다.
- **커밋 전 확인** — Python 3.10에서 기본 `TimeoutError`로는 비동기 타임아웃을 잡지 못하는 현상을 재현했습니다. `asyncio.TimeoutError`에 별칭을 붙여 두 예외를 구분했고, 개발 모드와 경고를 오류로 처리하는 설정으로 목업·재접속·종료를 다시 확인했습니다.
