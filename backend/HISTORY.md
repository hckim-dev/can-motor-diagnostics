## 2026-11-19 · 모의 CAN 명령과 운전 허가 검증

- **담당·근거** — Codex · [통신 규격](../docs/protocol.md), [CAN 2.1 프레임 예제](../tests/fixtures/can-2.1.jsonl), [모의 CAN 시험](../tests/check_can_control.py)
- **문제** — STM32 실물 송신 전에 TCP 조작을 CAN 명령·결과에 연결하고, STOP이 대기 명령과 연결 상실을 선점하는지 확인해야 했습니다.
- **판단과 변경** — 송신 인코더, 제어 상태, 모의 버스, TCP 연결을 분리했습니다. 송신 대기와 응답 마감을 각각 적용하고, 응답은 원래 epoch와 명령 순번을 대조합니다. 부팅 ID를 프로세스 사이에 보존하며, 모의 STOP 복구에서는 억제 송신 이후 더 큰 epoch의 정지 관측을 요구합니다.
- **검증** — Jetson Python 3.10.12에서 경고를 오류로 처리한 전체 44개 테스트를 통과했습니다. 모의 CAN의 네 명령, 순번 소진, STOP 선점, 지연 결과, 연결·세션 변경을 검증하고, TCP CLI로 가상 REAL의 시작·정지와 프로세스 재시작 시 부팅 ID 증가를 확인했습니다. 실제 CAN 송신, 어댑터의 송신 취소 범위, 실제 STOP 인과 확인은 미실행입니다.
- **재검토** — 정지 확인 없이 새 epoch에서 활성 상태가 관측되면 그 epoch에도 억제 프레임을 보내고 정지 확인 기준을 갱신합니다. 가상 모터에서 동일 CAN 명령의 결과 재사용, 이미 소비한 순번의 STOP 우선 처리, 허가 비트 해제 시 정지를 검증했습니다. Jetson에서 경고를 오류로 처리한 전체 47개 테스트를 통과했습니다.
- **단절·중복 요청 재검토** — 단절 통보 뒤에도 CAN 송신이 호출되는 문제와, 완료 결과가 대기 중일 때 동일 TCP 요청에 이전 `ACCEPTED`가 반환되는 문제를 재현했습니다. 명시적으로 재연결할 때까지 송수신을 막고, 대기 중인 최신 결과는 기존 송신 경로에서 전달합니다. 재연결 후 정지 재확인과 TCP 중복 요청을 회귀 시험에 추가했습니다. 모의 CAN을 포함한 전체 49개 테스트를 경고를 오류로 처리해 통과했습니다.
- **STOP 선점 재검토** — 같은 모의 버스 주기에 `START_REAL`과 `STOP`을 받으면 이미 큐에 넣은 `START_REAL`이 먼저 전달돼 가상 모터가 `RUNNING`에 진입했습니다. 명령 송신을 모의 버스 주기로 모아 STOP과 단절이 송신 전 명령을 취소할 수 있게 했습니다. STOP, TCP 단절, CAN 단절 각각에서 `START_REAL`이 가상 모터에 도달하지 않음을 검증했습니다. Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 50개 테스트를 통과했습니다.
- **만료 경계와 TCP 표시 재검토** — 300ms에 도착한 `MOTOR_STATE`가 이전 관측을 덮기 전에 만료를 적용해 허가를 철회하고 대기 명령을 취소합니다. 모의 버스에 전달된 조작 프레임을 수신 모듈에서도 관측해 TCP 조작 상태에 동일한 허가 유효기간을 적용했습니다. 상태 수신 299/300ms와 허가 표시 199/200ms 경계를 검증했습니다. Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 52개 테스트를 통과했습니다.
- **세션 카운터 소진 재검토** — 마지막 세션에서 STOP을 처리한 뒤 세션 번호가 0인 epoch가 생성되는 문제를 재현했습니다. 마지막 유효 epoch에서 `INTERNAL`을 한 번 기록하고 출력을 억제하며, 재허가와 `RESET`을 포함한 일반 명령을 거부합니다. REAL·TEST에서 마지막 세션의 정상 동작과 소진 이후 중복·신규 명령 거부를 검증했습니다. Linux aarch64의 Python 3.10.12에서 경고를 오류로 처리한 전체 53개 테스트를 통과했습니다.
- **명령 순번 소진 재검토** — `RESET`이 순번 255로 완료돼 가상 모터가 정지했는데도 다음 명령이 `SEQUENCE_EXHAUSTED`로 거부됐습니다. 마지막 순번을 소비하고 출력이 꺼져 있으면 기존 키로 결과를 만든 뒤 새 epoch를 발급합니다. 활성 상태에서는 STOP까지 현재 epoch를 유지합니다. 새 epoch에서 순번 1을 사용하고 이전 요청을 거부하는 동작을 검증했습니다. 경고를 오류로 처리한 전체 55개 테스트를 통과했습니다.
- **억제 송신 실패 재검토** — 첫 억제 프레임 제출이 실패하면 전송이 가능해져도 50ms를 기다려 STOP 명령이 타임아웃되는 문제를 재현했습니다. 억제 프레임은 다음 버스 주기에 재시도합니다. 송신이 빨리 복구되면 억제 프레임과 STOP 명령이 순서대로 전송되고, 명령 마감 이후에 복구되면 억제 프레임만 전송되는 것을 검증했습니다. 경고를 오류로 처리한 전체 56개 테스트를 통과했습니다.
- **CAN 허가 만료 고장 재검토** — 가상 모터에서 유효한 허가가 200ms 동안 없으면 출력은 정지했지만 `OP_LINK_LOSS`가 기록되지 않았습니다. 만료 시 고장 비트를 래치하고 새 epoch의 `FAULT` 상태를 발행합니다. 199/200ms 경계와 중복 고장 방지, CAN 재연결 이후 `RESET`과 새 `START_REAL`을 거쳐 복구하는 경로를 검증했습니다. 경고를 오류로 처리한 전체 57개 테스트를 통과했습니다.
- **가상 모터 수신 순서 재검토** — 주기 처리 전에 프레임을 받으면 200ms 경계에서 이전 허가를 연장하거나 구동 명령을 수락할 수 있었습니다. 주기 처리와 프레임 수신에서 같은 만료 처리를 사용합니다. 199ms 수신은 정상 처리하고 200ms 수신은 새 epoch로 전환한 뒤 이전 epoch의 허가와 명령을 거부하는 것을 검증했습니다. 경고를 오류로 처리한 전체 58개 테스트를 통과했습니다.
- **제어 상태 전이 구조 재검토** — 입력 전 타임아웃과 CAN 수신 후 epoch·허가 갱신을 분리했습니다. CAN 단절 전의 STOP 확인 기준으로 재연결 직후 허가가 복구되는 문제를 재현해, 단절 시 확인 기준을 폐기하도록 수정했습니다. TCP 연결 철회는 제어기 진입점으로 모았고 CAN 제어기와 가상 모터에서 동일한 허가 만료값과 상태 비트를 사용합니다. 재연결 이후의 억제와 정지 관측을 회귀 시험에 추가했고, 경고를 오류로 처리한 전체 59개 테스트를 통과했습니다.
- **HELLO 호환성 재검토** — CAN 2.0 `HELLO`의 큰 epoch·부팅 ID가 비교 기준에 반영돼, 이후 정상 CAN 2.1 세션이 거부되는 문제를 재현했습니다. 버전 불일치 시 상태·허가의 유효성은 철회하고 세션 비교 기준은 호환 버전에서만 갱신합니다. 정상 세션 복구와 이후 이전 세션 폐기를 회귀 시험으로 확인했으며, 경고를 오류로 처리한 전체 60개 테스트를 통과했습니다.
- **가상 모터 프레임 오류 재검토** — DLC가 잘못된 프레임을 모의 버스에 넣으면 디코딩 예외가 버스 처리까지 전파됐습니다. 가상 모터는 해당 프레임을 폐기하고 CAN ID별 오류 수를 기록합니다. 같은 버스 주기의 다음 정상 명령이 처리되고, 잘못된 허가로 200ms 만료가 연장되지 않는 것을 검증했습니다. 경고를 오류로 처리한 전체 62개 테스트를 통과했습니다.
- **4단계 통합 재검토** — 같은 스키마의 미지원 TCP 메시지 타입을 받으면 연결 종료로 운전 허가까지 철회될 수 있었습니다. 메시지 형식을 검증한 뒤 미지원 타입만 기록하고 건너뜁니다. 경고를 오류로 처리한 전체 62개 테스트와 별도 TCP 프로세스에서 가상 REAL의 시작·정지, 재접속 시 이전 요청 거부, 정상 종료를 확인했습니다.
- **Backend 전체 검수** — 가상 모터의 `MOTOR_STATE`가 시험 준비와 고장 출력 비트를 누락했습니다. `TEST_ARMED`·`TEST_ACTIVE`에서 `TEST_READY`, 고장이 래치된 상태에서 `DIAG_FAULT`를 보고합니다. 시험 준비 프레임을 CAN 2.1 공통 예제와 바이트 단위로 비교하고, 허가 만료 후 고장 상태 비트를 검증했습니다. 경고를 오류로 처리한 전체 63개 테스트와 읽기 전용 TCP CLI의 초기 응답·10Hz 주기·재접속을 확인했습니다.

## 2026-11-19 · CAN 수신과 측정 상태 검증

- **담당·근거** — Codex · [통신 규격](../docs/protocol.md), [시간순 CAN 예제](../tests/fixtures/can-rx-timed.jsonl), [CAN 수신 시험](../tests/check_can_rx.py)
- **문제** — TCP 목업의 고정 상태 대신 CAN 프레임에서 확인한 상태와 측정값을 표시하고, 결측·만료·이전 부팅의 값이 현재 상태로 남지 않게 해야 했습니다.
- **판단과 변경** — CAN 디코딩, 측정 결합, 세션 상태, 예제 공급을 분리했습니다. 수신 순번·단조 시각·원본 ID를 부여하고, 현재 부팅의 시간 프레임을 기준으로 100ms 안에 측정을 결합합니다. SOF나 어댑터 시각 대신 Jetson 수신 시각으로 유효 기간을 계산하며, 새 부팅과 연결 복구에서 300ms 동안 측정 결합을 보류합니다.
- **검증** — Jetson aarch64, Python 3.10.12에서 경고를 오류로 처리한 테스트 19건을 통과했습니다. CAN 필드·결측·만료·부팅·순번 경계와 CAN 예제에서 TCP 스냅샷까지의 흐름을 확인했습니다. `--can-fixture` 실행과 기존 읽기 전용 모드도 실제 TCP로 검증했습니다. 실물 CAN 어댑터의 지연과 CAN 송신은 미실행입니다.
- **재검토** — 이전 부팅의 시간 프레임은 폐기되지만 같은 순번의 미확정 측정값은 남아 새 부팅 샘플에 섞이는 경우를 재현했습니다. 시간 프레임에서 부팅이 다르다고 확인되면 그 순번의 미확정 묶음도 폐기합니다. 형식이 잘못된 프레임 뒤 정상 프레임이 결합 창 안에 오면 샘플 확정 전까지 교체할 수 있게 했습니다. 회귀 시험 2건을 추가해 Jetson에서 전체 21건을 통과했고, CAN 예제의 TCP 출력과 정상 종료를 다시 확인했습니다.
- **추가 경계 검증** — HELLO 만료 후 재수신만으로 이전 운전 허가가 되살아나는 경우를 재현했습니다. 같은 부팅·epoch에서는 이전 허가 순번을 기억하고 새 유효 순번을 받은 뒤에만 허가 상태를 갱신합니다. 오류가 있는 측정 프레임이 마지막에 와도 100ms 결합 창이 닫히기 전에는 확정하지 않습니다. Jetson에서 경고를 오류로 처리한 전체 23개 테스트를 통과했습니다.
- **연결 복구 검증** — 명시적으로 연결을 끊었다가 같은 모터 epoch와 조작 노드 부팅으로 복구할 때 중복 허가가 다시 유효해지는 경우를 수정했습니다. 연결 복구 시 이전 순번은 유지하고 새 순번의 wrap은 허용합니다. 모터 epoch나 조작 노드 부팅이 바뀌면 순번을 초기화합니다. Jetson에서 경고를 오류로 처리한 전체 25개 테스트를 통과했습니다.
- **최종 재검토** — 고장 표시 캐시와 마지막으로 수락한 고장 순번·마스크를 분리했습니다. 같은 epoch에서 연결 단절, HELLO 만료, 버전 불일치로 복구한 뒤에도 이전 고장은 거부합니다. 같은 순번·마스크의 반복 보고, 순번 wrap, 새 epoch 초기화를 회귀 시험에 포함했습니다. Jetson에서 경고를 오류로 처리한 전체 26개 테스트를 통과했고, 8비트 순번 256개 시작값에서 재연결 후 이전·모호 순번 거부와 정상 보고를 확인했습니다.
- **종결 검증** — 조작 노드의 새 부팅 ID를 먼저 받은 경우 기존 모터 epoch의 지연된 허가가 다시 유효해지는 문제를 수정했습니다. 더 큰 모터 epoch의 HELLO와 해당 epoch의 새 허가를 모두 받아야 허가 상태를 갱신합니다. Jetson에서 경고를 오류로 처리한 전체 28개 테스트를 통과했습니다.

- **문제** — Qt 앱과 CAN 연결 전에 시험 준비 명령과 heartbeat 만료, 재접속 시 요청 처리를 검증할 필요가 있었습니다.
- **판단과 변경** — `--control`에서 단일 제어 연결을 받고, `ARM_TEST` 결과와 `TEST_ARMED` 관측을 나눠 보냅니다. 유효 heartbeat가 300ms 없으면 준비를 해제합니다. 재접속 전의 요청이 다시 실행되지 않도록 목업 프로세스에 최대 255건을 보관하고, 한도 이후 새 요청은 거부합니다.
- **검증** — Jetson aarch64, Python 3.10.12에서 개발 모드와 경고를 오류로 처리하는 설정으로 조작 목업 시험 5건을 통과했습니다. 분할·합쳐진 입력, 결과와 상태, 만료, 중복·상한, 이전 연결 요청, 인자·프레이밍 오류, 동시 접속 및 종료를 확인했습니다. 읽기 전용 스냅샷 10Hz와 재접속도 재검증했습니다. Qt와 실물 CAN·UART 검증은 미실행입니다.
- **종결 검토** — TCP 입출력과 조작 상태를 별도 모듈로 분리했습니다. 잘못된 인자로 거부된 요청의 ID를 재사용하면 실행되던 문제를 재현해 최초 거부 결과도 기록하도록 수정했습니다. 같은 ID로 같은 잘못된 요청은 이전 결과를 받고, 인자를 고친 요청은 충돌로 거부됩니다. Jetson에서 조작 시험 6건을 두 차례 통과했고 읽기 전용 10Hz 전송과 재접속도 다시 확인했습니다.
- **구조 검토** — 거부된 요청까지 세던 `cmd_seq`를 요청 기록과 분리해 성공한 새 요청에만 순번을 발급합니다. 명령별 인자 범위는 한 곳에서 관리하고, 테스트의 첫 성공 응답은 공통 fixture와 대조합니다. 만료 후 다시 준비하거나 재접속해도 같은 epoch에서 순번이 이어짐을 확인했습니다. Jetson에서 경고를 오류로 처리한 조작 시험 6건을 두 차례 통과했고, 읽기 전용 모드도 다시 확인했습니다.

## 2026-11-19 · 읽기 전용 TCP 목업 검증

- **담당·근거** — Codex · [통신 규격](../docs/protocol.md), [TCP 예제](../tests/fixtures/tcp-backend-to-qt.jsonl), [목업 실행 및 검증 방법](README.md)
- **문제** — Qt 앱을 개발하기 전에 Backend의 초기 상태와 TCP 메시지 경계를 Jetson에서 독립적으로 확인할 필요가 있었습니다.
- **판단과 변경** — 표준 라이브러리로 읽기 전용 서버와 검증 클라이언트를 구현했습니다. 공통 예제와 수신 내용을 대조하고, 연결마다 `stream_id`를 발급합니다. 검토 과정에서 연결이 열린 상태의 종료 문제를 확인해 종료 시 활성 연결을 닫도록 수정했습니다. 검증 클라이언트는 이전 연결의 EOF 처리와 재접속이 겹쳐 새 연결이 `hello` 전에 닫히면 짧게 재접속합니다.
- **검증** — Jetson aarch64, Python 3.10.12에서 6회 실행했습니다. 각 실행에서 `hello → TEST / STOPPED`, 스냅샷 10간격 약 1.02초, 재접속 시 새 `stream_id`를 확인했습니다. 분할·합쳐진 메시지, LF 포함 16,384바이트 경계, 미완성 줄과 NaN 거부, 두 번째 연결 및 클라이언트 입력 차단, 활성 연결 중 SIGINT·SIGTERM 정상 종료를 확인했습니다. CAN·UART 실물 및 Windows 클라이언트 실행은 미실행입니다.
- **종결 검토** — Python 3.10에서 첫 스냅샷 이후 대기 시간이 지나면 연결이 끊기는 현상을 재현해 `asyncio.TimeoutError`를 처리하도록 수정했습니다. 검증 클라이언트는 전체 평균과 함께 스냅샷 사이의 송신 시각 차이도 확인합니다. 1초 지연 후 10개를 몰아 보낸 입력은 거부했고, 수정 후 Jetson에서 목업 6회와 접속·종료·프레이밍 검증을 통과했습니다. 쓰기 대기가 만료되면 연결 슬롯을 반환하는 동작은 모의 writer로 확인했습니다.
- **커밋 전 확인** — Python 3.10에서 기본 `TimeoutError`로는 비동기 타임아웃을 잡지 못하는 현상을 재현했습니다. `asyncio.TimeoutError`에 별칭을 붙여 두 예외를 구분했고, 개발 모드와 경고를 오류로 처리하는 설정으로 목업·재접속·종료를 다시 확인했습니다.
